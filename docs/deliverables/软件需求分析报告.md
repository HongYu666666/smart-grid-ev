## 1. 引言

### 1.1 编写目的

本报告把任务书和实施方案中的课题目标、考核方式与 2026 年 7 月正式计划
转化为电动汽车承载力提升单场景的可追踪软件需求，供后续统一数据模型、
系统总体设计、模块级 OpenSpec、实现和测试共同使用。

报告保持 `REQ-EV-001`—`REQ-EV-012` 稳定编号，与
[`典型场景-业务需求-孪智功能映射表.md`](典型场景-业务需求-孪智功能映射表.md)
一致，不建立第二套需求编号。

### 1.2 建设目标

新系统面向配电系统典型场景，形成“场景数据加载—孪生状态推进—智能体动作
提案—安全校验—执行或拒绝—结果与指标归档”的可重复仿真链路。电动汽车
承载力提升是首个端到端场景，用于沉淀后续场景可复用的模块、数据、接口、
安全校验和证据方法。

当前阶段目标是形成单场景需求基线，不宣称运行时系统已经实现。任务书最终
考核中的多场景覆盖、连续 `24×7` 小时推演、平均业务需求覆盖率和安全校验
功能类型，在本报告中作为后续系统验收约束保留，不在需求初稿阶段提前报为完成。

## 2. 综合描述

### 2.1 系统边界

新系统范围内包括：

- 场景配置、数据接入、统一对象注册和统一时钟；
- 配电网、常规负荷、车辆、交通和充电设施的事实状态及演化；
- 智能体注册、状态观察、预测/优化和结构化动作提案；
- Schema、时序、物理和业务安全校验；
- 动作执行/拒绝、失败回退、事件记录、结果存储和指标计算；
- 面向业务需求覆盖率和安全校验的可复现实验与证据归档。

新系统范围外包括：

- 电网真实生产控制、保护装置闭环和真实市场结算；
- 未经批准的多场景详细模型；
- 把参考项目的内部类、数据文件或运行结果直接当作正式接口和验收结果；
- 在统一数据模型获批前固化 pandapower、OpenDSS、V2Sim 等候选内部对象。

### 2.2 技术边界

当前批准的总体技术边界为：

```text
配电网主仿真内核
        ↕ 统一适配接口
Python 编排 / 孪智交互 / 安全校验 / 结果与评估层
        ↕ 场景接口
电动汽车、交通、充电设施和其他场景适配器
```

配电网 PoC 首选 pandapower，V2Sim 可提供 EV 出行、交通、充电与 V2G
参考能力，但二者都不能绕过新系统的统一数据模型、动作校验和证据边界。

### 2.3 参与者与职责

| 参与者 | 责任 |
| --- | --- |
| 软件负责人（lead） | 维护系统级 OpenSpec、跨模块契约、需求追踪、接口裁定和最终验收 |
| 组员（member） | 基于上层 change 细化模块级 OpenSpec，完成调研、实现、测试与证据整理 |
| Reviewer | 检查范围、语义、证据和实现，不替作者补写未完成成果 |
| 场景研究/业务人员 | 提供业务流程、数据口径、动作与指标解释，确认待裁定业务假设 |
| 智能体/策略开发者 | 产生结构化提案和解释，不拥有直接修改孪生状态的权限 |
| 仿真与数据组件 | 按批准的输入推进事实状态，返回结构化结果和错误 |

### 2.4 运行环境

目标系统以可版本化的 Python 编排层为主，配电网内核、EV/交通模型和其他
场景工具通过适配接口接入。正式运行环境必须记录操作系统、Python 和依赖
版本、后端名称/版本、配置和输入哈希、随机种子、开始/结束时间及退出状态。

开发和验收不得依赖个人绝对路径、未登记本地文件、交互式 GUI 手工步骤或
无法复现的临时环境。可视化是结果呈现方式，不替代结构化运行证据。

### 2.5 约束

- 所有对象必须使用稳定、唯一、可追踪的标识；
- 数据必须声明单位、时区/时标、采样周期、版本和缺失值语义；
- 智能体只能提出动作，孪生与安全校验层拥有最终接受/拒绝和状态提交权；
- 任一校验失败不得产生部分状态提交，执行失败必须回退到上一稳定状态或安全状态；
- 参考证据与新系统证据必须分栏记录；
- 最终多场景推演需要满足任务书的连续 `24×7` 小时、平均业务需求覆盖率不低于 95% 和不少于 8 类功能安全校验要求；
- 当前单场景阶段必须保存可扩展到多场景的对象、事件、动作、指标和证据接口。

### 2.6 假设与待裁定事项

- 当前只批准电动汽车承载力提升单场景；其他场景仅保留扩展接口。
- pandapower 只被批准为下一阶段可删除 PoC 的首选候选，不是最终生产内核。
- 交通仿真路线、三相不平衡配网方案、指标阈值和不少于 8 类安全校验的最终分类仍待后续 change 裁定。
- 项目正式数据尚未齐备；缺失项必须进入基础数据清单，不能用参考项目样例静默补齐。

## 3. 单场景业务需求

### 3.1 核心对象

| 类别 | 核心对象 | 关键事实状态 |
| --- | --- | --- |
| 场景与实验 | 场景、实验配置、运行实例、统一时钟 | 版本、时间范围、时间步、随机种子、运行状态 |
| 配电网 | 母线、支路、变压器、外部电网、负荷、新能源、储能 | 拓扑、参数、开关/可用状态、电压、功率、载流、越限 |
| 交通与车辆 | 交通节点/边、道路事件、车辆、行程 | 位置、路径、速度/路时、SOC、电池、行程与驻留状态 |
| 充电设施 | 充电站、充电桩、队列、充放电会话 | 可用性、桩型、功率、占用、排队、能量和计量状态 |
| 孪智交互 | 状态快照、动作提案、校验结果、执行结果 | 提议者、时标、版本、接受/拒绝原因、回退状态 |
| 事件与结果 | 事件、状态历史、指标、证据记录 | 顺序、时间、影响对象、来源、结果值、哈希和证据等级 |

### 3.2 输入、状态、事件和动作

输入至少覆盖配电网拓扑与参数、常规负荷、新能源、车辆/行程、交通网络、
充电设施、跨域映射、场景配置、事件、候选动作、约束和指标定义。

事件至少覆盖场景初始化、时间推进、车辆出发/到达、排队、充电开始/结束、
负荷变化、道路/设备/站点异常、通信延迟、智能体不可用和恢复。

动作至少覆盖充电站选择、目标 SOC、充放电模式、功率/时段、负荷削减或
移峰、需求响应和保底控制。每个动作必须具有提议者、目标对象、有效时刻、
参数、策略版本和校验结果。

### 3.3 正常流程

1. 加载版本化场景配置和输入，校验 Schema、单位、时标与对象引用。
2. 创建配电网、车辆、交通和充电设施初始事实状态。
3. 按统一时钟推进确定性事件和物理状态。
4. 发布带版本和时标的状态快照。
5. 智能体或人工产生结构化动作提案。
6. 依次执行数据、时序、资源、SOC、功率、潮流和业务约束校验。
7. 接受合法动作并原子提交状态；拒绝非法动作并保留拒绝原因。
8. 记录事件、输入、动作、状态、结果、错误和运行元数据。
9. 计算场景指标、需求覆盖和安全校验证据，支持归档与回放。

### 3.4 异常与回退

| 异常 | 最低处理要求 |
| --- | --- |
| 输入缺失、单位或对象引用冲突 | 拒绝启动并报告具体字段，不自动借用参考数据 |
| 非法/过期动作 | 拒绝且不修改状态，返回结构化原因 |
| 潮流不收敛或物理越限 | 拒绝动作或执行获批保底控制，保存求解和裁决证据 |
| 车辆/站点/道路故障 | 进入确定性故障状态，允许经校验的重调度或替代方案 |
| 智能体超时或不可用 | 使用人工/规则保底策略，不中断事实状态记录 |
| 执行中失败 | 不允许半提交；回退上一稳定状态并记录失败阶段 |
| 回放差异超阈值 | 拒绝“可复现”结论，保留输入、版本和差异报告 |

## 5. 指标与验收证据

### 5.1 单场景指标组

- EV/服务：服务车辆数、充电完成率、等待时间、SOC、能量、费用和未服务量；
- 配电网：节点电压、线路/变压器负载率、网损、越限次数与时长、潮流收敛；
- 交通/站点：行程时间、可达性、拥堵度、桩占用率、队列长度和吞吐；
- 交互/安全：动作接受率、拒绝原因、回退次数、异常检测与恢复时间；
- 架构/证据：运行时间、接口响应、事件完整率、回放差异、需求覆盖率和安全校验覆盖。

指标定义必须包含名称、含义、单位、时间窗口、聚合方法、缺失值处理、基准方案
和证据路径。当前报告只定义最低范围，具体字段由统一数据模型 change 细化。

### 5.2 最终考核约束

- 每个典型场景的业务需求覆盖率按“通过测试的业务需求数/该场景业务需求总数”计算；
- 架构平均业务需求覆盖率按任务书方法跨场景汇总，最终不得低于 95%；
- 每个典型场景的正式仿真推演时间不少于连续 `24×7` 小时；
- 安全校验最终覆盖的功能类型不少于 8 类；
- 每个通过结论必须能回链到版本化输入、配置、动作、事件、结果和测试记录。

单一 EV 场景阶段可以先验证计算链路，但不能用单场景结果提前宣称多场景最终
指标已经满足。
