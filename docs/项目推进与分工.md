# 项目推进与分工

更新日期：2026-07-14

本项目固定由软件负责人 1 人、组员 2 人推进。管理上只区分“负责人做什么、组员做什么”，采用“两周成果窗口 + Issue 自主推进”的方式，不把每天排死。软件负责人维护成果边界和验收口径，两名组员作为一个执行小组，在已批准范围内自行拆解步骤、协商分工、安排时间和使用 Codex。

## 1. 固定职责

| 角色标识 | 主责范围 | 不承担的责任 | Reviewer |
| --- | --- | --- | --- |
| `lead` | 进度计划、OpenSpec、需求收敛、孪智功能映射、接口决策、文档归档、最终验收 | 不包办组员的调研和模块实现 | 至少一名组员 Review |
| `member` | 两名组员共同承担调研、开源项目分析、实现、测试和证据整理，并自行协商具体分工 | 不自行扩大 OpenSpec 范围，不单方面修改公共接口 | 另一名组员或 lead Review |

不在本文件中登记两名组员的姓名、账号或固定技术方向；后续以实际 Git 提交、Issue 和 PR 记录识别贡献者。每个 Issue 只需要明确当次直接负责人，下一项任务可以重新分配。

## 4. 推进节奏

- 窗口开始：lead 说明目标成果、非目标和最低证据，不规定每天必须完成什么。
- 窗口中段：负责人和组员进行一次短检查，决定继续、缩小范围或补充资源。
- 日常：组员自主安排；出现影响别人、需要接口裁定或连续一天无法推进的阻塞时，在 Issue 留言。
- 窗口结束：交叉 Review，lead 按 OpenSpec 和证据验收；未完成部分进入下一窗口，不用虚构完成百分比。
- 双周：使用 `docs/软件组双周推进模板.md` 汇总正式成果。

推荐看板状态：`Backlog → Ready → In Progress → In Review → Acceptance → Done`，阻塞任务单独标为 `Blocked`。

## 5. 验收边界

实现者可以声明“已提交、待验收”，Reviewer 可以声明“Review 通过”，只有 lead 可以声明“已验收”。正式进度表中的完成进度只依据已验收成果更新，不依据口头百分比或 Codex 自检结论更新。
