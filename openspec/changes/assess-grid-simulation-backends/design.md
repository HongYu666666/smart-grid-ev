## Context

正式计划把 V2Sim 典型案例运行与配电网仿真工具选型放在 2026 年 7 月 18—24 日。本 change 只管理该周两项正式成果；未在计划窗口内达到高证据等级的内容保持未完成或转入后续 PoC，不通过修改正式日期、降低证据标准或沿用上一周 Issue 来制造完成状态。

仓库包含 V2Sim 源码快照和早期世界模型调研，但这些项目只作为新系统重新开发时的候选参考，不是代码或验收 baseline。现有结论主要来自资料分析，候选项目未使用统一标准和证据等级。团队只有两名固定组员，因此评估流程必须轻量、可并行，并允许因平台/依赖问题保留未完成验证。

## Goals / Non-Goals

**Goals:**

- 形成可复现的 V2Sim 代表性案例运行记录。
- 使用一致维度比较主要配电网仿真候选项目。
- 明确“读过资料”“安装成功”“跑过案例”“用项目数据验证”的差别。
- 在本周成果验收时形成能指导下一轮 PoC 的阶段建议。
- 保留不确定性，不用虚假精确评分或日期压力替代证据。
- 将候选项目证据与新系统实现证据分开，不因候选案例运行成功而提高新系统完成度。

**Non-Goals:**

- 不完成生产级内核集成。
- 不要求在所有操作系统上验证全部候选项目。
- 不要求本周内选择唯一工具。
- 不将临时试验依赖写入正式运行环境。
- 不把任何候选项目指定为新系统代码基线；后续采用工具也必须通过新系统定义的适配接口和独立测试。

## Decisions

### 1. 采用证据等级而不是单一总分

每个候选项目的每项关键能力使用以下等级：

| 等级 | 含义 | 最低证据 |
| --- | --- | --- |
| `E0` | 尚未确认 | 无官方来源或仅有待核线索 |
| `E1` | 官方资料确认 | 官方文档、仓库、发布或许可证 |
| `E2` | 本地安装/导入确认 | 环境、版本、命令和成功输出 |
| `E3` | 最小案例运行确认 | 输入、命令、输出和结果检查 |
| `E4` | 项目数据/接口验证 | 候选项目的数据映射、接口试验和可复现结果；仍不代表新系统已实现 |

不使用一个综合分数决定工具，因为早期评分会掩盖候选项目在“快速编排”“工程校核”“多相不平衡”“跨语言集成”等不同职责上的差异。

### 2. 使用同一评价矩阵

报告至少包含：

- 项目与官方来源；
- 版本、维护状态和许可证；
- 配电网对象与分析能力；
- 时序、事件、控制和批量实验能力；
- Python/其他语言接口与部署方式；
- 所需输入数据和工程参数；
- 可复现性、性能和平台限制；
- 与 Python 编排层、EV 场景适配器的边界；
- 证据等级、失败记录和下一步 PoC。

### 3. 试验在隔离环境进行

候选项目验证使用单独虚拟环境、容器或临时目录。试验成果只提交小型脚本、配置、日志摘要和文档。参考项目的目录结构、示例工程和依赖不进入新系统源码；任何正式依赖、适配接口或公共接口变化另开 implementation change。

### 4. 本周工作只拆成 lead 与 member 两部分

#### Part A：lead — 配电网仿真工具选型与验证报告

`lead` 独立负责 `docs/deliverables/配电网仿真工具选型与验证报告.md`，报告必须包含：

1. 文档范围、评估日期、负责人、Reviewer 和候选清单；
2. E0—E4 证据等级、结论用语和淘汰门槛；
3. OpenDSS、GridLAB-D、pandapower、PowerModelsDistribution 的官方来源、评估版本/提交、维护状态和许可证；
4. 统一评价维度：配网建模范围、求解能力、时序/控制、编程接口、平台依赖、输入输出、性能/连续运行、可复现性、EV 场景适配、Python 编排边界和风险；
5. 逐候选证据记录与统一比较矩阵，不使用无法解释的综合分数；
6. 与 `REQ-EV-005`、`REQ-EV-007`、`REQ-EV-009`、`REQ-EV-011`、`REQ-EV-012` 的对应关系；
7. 基于统一证据选出一个进入 PoC 的首选后端和必要的备选，不把首选写成最终生产内核；
8. “继续 PoC、保留候选、暂缓、淘汰”的阶段建议及下一验证动作；
9. 数据模型、适配器和后续 PoC 的输入、依赖、未决问题与已知限制；
10. `docs/reference_catalogs/grid_backend/<selected-project>/` 中首选后端的完整函数、类和方法目录；报告正文只保留目录入口和开发结论，不重复粘贴逐符号内容。

`lead` 只需要对四个候选完成足以支持 PoC 选择的统一比较，不为四个候选全部建立代码目录。完整目录只覆盖进入 PoC 的首选后端。`lead` 可以引用 member 的 V2Sim 证据，但不得代写或自行宣称 V2Sim 已运行。

#### Part B：member — V2Sim 典型案例运行记录

`member` 的当前直接负责人由 GitHub Issue 记录，独立负责 `docs/deliverables/V2Sim典型案例运行记录.md`，报告必须包含：

1. 文档范围、负责人、Reviewer、仓库提交和 V2Sim 版本；
2. 代表性案例选择理由、案例路径、配置、输入文件和生成步骤；
3. 操作系统、Python、关键外部程序、依赖版本和隔离方法；
4. 实际执行的安装、生成、运行和结果查看命令，不把拟执行命令写成已执行；
5. 车辆、交通、快/慢充、充电负荷、配网、控制动作和评价指标的主要输入输出；
6. 输出目录、关键文件、运行时间、退出状态和结果合理性检查；
7. 失败命令、错误摘要、最深验证步骤、E0—E4 证据等级和环境限制；
8. V2Sim 与配网主仿真内核、Python 编排层和新系统验收边界；
9. Reviewer 可从干净环境复现的步骤，以及不应提交的缓存、二进制和大体积结果；
10. `docs/reference_catalogs/v2sim/` 中固定版本 V2Sim 的完整函数、类和方法目录；报告正文只保留目录入口和案例运行结论，不重复粘贴逐符号内容。

两部分分别使用一个 Issue、一个短期分支和一个 PR。作者完成自检后由另一角色 Review，`lead` 做最终验收；不再使用 `member-a/member-b`、额外分工表或上一周 Issue。

### 5. 代码目录采用统一结构并自动校验完整性

每个最终目录使用以下结构：

```text
docs/reference_catalogs/<project>/
├── README.md
├── symbols.csv
├── coverage.md
└── modules/
    └── <module-or-source-path>.md
```

- `README.md`：项目身份、官方来源、固定版本/提交、语言、扫描范围、生成命令、目录使用方法和新系统参考边界；
- `symbols.csv`：机器可读的完整清单，每行一个函数、类或方法；
- `coverage.md`：扫描文件数、符号总数、按类型计数、未解析文件、排除项和完整性检查结果；
- `modules/`：按模块或源文件组织的人类可读目录，列出该模块内每个函数、类和方法的功能。

每个符号至少包含：

| 字段 | 含义 |
| --- | --- |
| `kind` | function / class / method |
| `qualified_name` | 稳定限定名 |
| `signature` | 参数与返回签名；无法静态解析时记录原因 |
| `source_anchor` | 固定版本下的源码相对路径与行号 |
| `visibility` | public / private / internal |
| `summary` | 该符号实际负责什么 |
| `inputs_outputs` | 主要输入、输出和数据结构 |
| `side_effects` | 文件、网络、进程、全局状态或仿真状态副作用 |
| `dependencies` | 关键内部/外部依赖 |
| `development_relevance` | 对新系统可参考、需适配、仅内部或不建议复用 |
| `evidence_status` | 源码确认、文档确认、运行确认或待人工补充 |
| `review_status` | 自动生成、抽检通过或人工复核 |

扫描范围默认包含固定版本生产源码中的全部模块级函数、类和类方法，包括私有符号；测试、示例、vendored 第三方、生成代码和构建产物默认排除，但必须在 `coverage.md` 中逐类记录。没有文档或无法解释的符号必须保留并标记“待人工补充”，不得静默遗漏。

目录先由语言适配的静态分析脚本自动生成 `symbols.csv`、逐符号功能初稿和模块骨架。每个符号的 `summary` 均不得为空；无法从名称、签名、文档和源码行为可靠判断时，保留符号并明确写出待确认点，不虚构功能。

人工复核按开发相关性分级：

- 对新系统“可直接参考”或“需要适配”的核心模块、公共入口及其关键调用链逐项人工复核；
- 对内部支撑模块按模块抽检，检查功能描述、输入输出、副作用和源码锚点；
- 测试、示例、vendored、生成代码和构建产物不逐符号整理，但在 `coverage.md` 记录排除范围与理由。

验收时将固定版本源码扫描结果与目录限定名集合比较，要求无遗漏、无重复，并记录未解析文件。全量完整性由工具保证，人工时间集中在后续开发真正会使用的模块；不要求人工从零抄写全部符号。

### 6. 结论采用阶段状态

允许的阶段状态为：`继续 PoC`、`保留候选`、`暂缓`、`淘汰`。只有在官方限制或充分实测证据下才使用“淘汰”；环境暂时不具备只应标为“暂缓”或“待验证”。

## Evidence Record

每次最小验证记录：

| 字段 | 说明 |
| --- | --- |
| `project` | 项目名称与官方 URL |
| `version` | 版本或提交 |
| `environment` | OS、运行时、关键外部程序 |
| `input` | 示例模型/配置及来源 |
| `command` | 可复制的安装与运行命令 |
| `output` | 关键输出位置和摘要 |
| `check` | 如何判断成功或结果合理 |
| `evidence_level` | E0—E4 |
| `limitations` | 失败、缺失数据或适用边界 |

## Risks / Trade-offs

- [候选项目跨语言/跨平台，环境搭建耗时] → 优先 E1/E2，选择最有价值的候选做到 E3，不要求全部一次跑通。
- [把无法安装误判为工具能力不足] → 失败结论限定为当前环境，并保留官方能力证据与下一步环境要求。
- [开源项目状态变化] → 记录评估日期、版本/提交和官方来源。
- [两份报告重复或互相覆盖] → OpenSpec 固定报告内容合同，V2Sim 实测归 member、配网候选比较归 lead，通过链接共享证据。
- [全量代码目录工作量失控] → 四个候选只做统一比较；完整符号目录只覆盖 V2Sim 和首选 PoC 后端，并以自动提取保证完整性。
- [固定版本符号数量很大，逐项手写不可持续] → 全量符号自动生成非空功能初稿，核心开发链路逐项人工复核，内部模块按模块抽检并保留 `review_status`。
- [目录只摘录公开 API，后续开发仍需翻源码] → 生产源码中的 public/private/internal 函数、类和方法均进入清单，排除项单独记录。
- [为了赶进度直接选型] → 本周允许保留多个候选和组合路线。
- [试验依赖污染项目] → 隔离环境，生产依赖变化必须另开 change。

## Migration Plan

1. lead 确认评价矩阵、候选范围和两份报告内容合同。
2. member 在个人 fork 的独立研究分支完成 V2Sim 运行记录并提交 PR。
3. lead 在主仓库短期分支完成配网后端选型报告并提交 PR。
4. 两份 PR 互相引用；member Review lead 报告的可复现性，lead Review member 报告的证据等级和边界。
5. lead 验收本周两份成果，并把未解决项转成后续 PoC、接口或数据模型 Issue。
6. 只有后续 implementation change 批准后，才可通过新系统独立定义的适配器接入选定工具，并以新系统测试结果作为验收证据；候选项目本身仍不是代码 baseline。

本 change 只产生文档、小型验证脚本和证据，因此回滚时删除对应成果/试验文件即可，不影响现有运行原型。
