## Context

正式计划把 V2Sim 典型案例运行与配电网仿真工具选型放在 2026 年 7 月 18—24 日。团队希望从 7 月 14 日开始提前预研，并将需求基线和工具评估合并为约两周的成果窗口，而不是按天卡死。

仓库包含 V2Sim 源码快照和早期世界模型调研，但现有结论主要来自资料分析，候选项目未使用统一标准和证据等级。团队只有两名固定组员，因此评估流程必须轻量、可并行，并允许因平台/依赖问题保留未完成验证。

## Goals / Non-Goals

**Goals:**

- 形成可复现的 V2Sim 代表性案例运行记录。
- 使用一致维度比较主要配电网仿真候选项目。
- 明确“读过资料”“安装成功”“跑过案例”“用项目数据验证”的差别。
- 在两周末形成能指导下一轮 PoC 的阶段建议。
- 保留不确定性，不用虚假精确评分或日期压力替代证据。

**Non-Goals:**

- 不完成生产级内核集成。
- 不要求在所有操作系统上验证全部候选项目。
- 不要求两周内选择唯一工具。
- 不将临时试验依赖写入正式运行环境。

## Decisions

### 1. 采用证据等级而不是单一总分

每个候选项目的每项关键能力使用以下等级：

| 等级 | 含义 | 最低证据 |
| --- | --- | --- |
| `E0` | 尚未确认 | 无官方来源或仅有待核线索 |
| `E1` | 官方资料确认 | 官方文档、仓库、发布或许可证 |
| `E2` | 本地安装/导入确认 | 环境、版本、命令和成功输出 |
| `E3` | 最小案例运行确认 | 输入、命令、输出和结果检查 |
| `E4` | 项目数据/接口验证 | 项目数据映射、接口试验和可复现结果 |

不使用一个综合分数决定工具，因为早期评分会掩盖候选项目在“快速编排”“工程校核”“多相不平衡”“跨语言集成”等不同职责上的差异。

### 2. 使用同一评价矩阵

报告至少包含：

- 项目与官方来源；
- 版本、维护状态和许可证；
- 配电网对象与分析能力；
- 时序、事件、控制和批量实验能力；
- Python/其他语言接口与部署方式；
- 所需输入数据和工程参数；
- 可复现性、性能和平台限制；
- 与 Python 编排层、EV 场景适配器的边界；
- 证据等级、失败记录和下一步 PoC。

### 3. 试验在隔离环境进行

候选项目验证使用单独虚拟环境、容器或临时目录。试验成果只提交小型脚本、配置、日志摘要和文档。任何生产依赖或公共接口变化另开 implementation change。

### 4. 两名组员按主成果并行，允许协作互换

- `member-a` 默认负责 V2Sim 代表性案例和 EV/配网输入输出边界；
- `member-b` 默认负责 OpenDSS、GridLAB-D、pandapower、PowerModelsDistribution 的统一矩阵和最小可行性验证；
- `lead` 负责确认评价维度、处理范围裁定和验收阶段建议。

如果成员环境更适合某个候选项目，可以在 Issue 中交换验证项；分工不按每天冻结，但每个 PR 只保留一个主成果。

### 5. 结论采用阶段状态

允许的阶段状态为：`继续 PoC`、`保留候选`、`暂缓`、`淘汰`。只有在官方限制或充分实测证据下才使用“淘汰”；环境暂时不具备只应标为“暂缓”或“待验证”。

## Evidence Record

每次最小验证记录：

| 字段 | 说明 |
| --- | --- |
| `project` | 项目名称与官方 URL |
| `version` | 版本或提交 |
| `environment` | OS、运行时、关键外部程序 |
| `input` | 示例模型/配置及来源 |
| `command` | 可复制的安装与运行命令 |
| `output` | 关键输出位置和摘要 |
| `check` | 如何判断成功或结果合理 |
| `evidence_level` | E0—E4 |
| `limitations` | 失败、缺失数据或适用边界 |

## Risks / Trade-offs

- [候选项目跨语言/跨平台，环境搭建耗时] → 优先 E1/E2，选择最有价值的候选做到 E3，不要求全部一次跑通。
- [把无法安装误判为工具能力不足] → 失败结论限定为当前环境，并保留官方能力证据与下一步环境要求。
- [开源项目状态变化] → 记录评估日期、版本/提交和官方来源。
- [组员各写一套评价标准] → lead 先确认统一矩阵，A/B 在同一字段下填证据。
- [为了赶进度直接选型] → 允许两周末保留多个候选和组合路线。
- [试验依赖污染项目] → 隔离环境，生产依赖变化必须另开 change。

## Migration Plan

1. lead 确认评价矩阵和候选范围。
2. member-a/member-b 在个人 fork 的独立研究分支收集证据并提交两个主成果 PR。
3. A/B 交叉 Review 证据等级、复现步骤和结论边界。
4. lead 验收报告初版，并把未解决项转成下一窗口的 PoC Issue。
5. 只有后续 implementation change 批准后，才将选定工具接入统一数据模型和运行框架。

本 change 只产生文档、小型验证脚本和证据，因此回滚时删除对应成果/试验文件即可，不影响现有运行原型。

- 哪些候选项目能够在当前窗口做到 E3，哪些只适合 E1/E2？
- 现有配电网数据是否足以开展 E4，还是需要先完成数据模型和参数补齐？
- 阶段版更重视快速 Python 集成还是工程高保真校核，是否需要双层工具路线？
