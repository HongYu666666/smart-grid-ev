## Context

已接受的 `unified-ev-grid-data-model` 固定了公共语义内核：稳定身份、`run_id`、
时间与单位、schema/生产者版本、来源与质量、跨域引用完整性、事件与动作生命周期、
结构化结果/错误、指标与运行证据。它显式声明字段名、存储结构、序列化方式和模块
内部状态机由成员模块级 change 决定。

`docs/deliverables/电动汽车场景基础数据清单.md` 已经逐项登记七类数据的对象 ID、
单位、时间粒度、来源、证据等级、缺口和后续模块归属，并映射到
`REQ-EV-001`—`REQ-EV-012` 与上层 11 项 Requirement。清单的定位是来源/缺口账本，
不是运行时可校验的输入契约。

因此本模块要解决的问题是：把“账本”转成“可判定的入口合同”。判定必须覆盖三种
现实情况，而不是只处理理想输入：

1. 正式项目数据尚未取得，当前可用输入均为 v1、V2Sim、pandapower 参考资产；
2. 区域数据包只能登记标识、大小和 SHA-256，不进入 Git；
3. `jun30` parity 基线文件未交付且无哈希，其零误差结果只能作为 member 侧参考
   运行证据，不能作为新系统数据基线或独立复现声明。

本 change 只定义模块外部可观察行为与契约。运行时实现、CLI 入口和网页展示分别
属于后续实现 change 与 Issue #23 的 lead 范围。

## Goals / Non-Goals

**Goals:**

- 让一批场景输入可以被明确判定为“可用”“受限可用”或“拒绝”，且判定原因可定位到
  具体数据集、对象和字段。
- 让缺失、受限和无完整性证据的数据显式表达为质量状态或错误，而不是静默兜底。
- 让仓库外受限数据可以被引用和校验，同时不把数据文件、密钥或个人路径入库。
- 让同一次运行的输入可回放：输入清单、版本、哈希、转换记录和种子引用齐备。
- 让下游孪生初始化、动作校验和结果模块只依赖公共输入视图，不读取参考项目私有格式。
- 保留 member 在模块内部的设计自由度，同时明确哪些语义必须先修订上层 spec。

**Non-Goals:**

- 不选择序列化库、配置语言、数据库或目录结构。
- 不定义领域内部状态机、潮流算法、排队算法和交通模型。
- 不定义动作校验规则集与安全校验分类。
- 不实现受限数据的分发、脱敏或权限审批流程。
- 不承担 `REQ-EV-002`—`REQ-EV-005` 的状态演化职责。
- 不产生长周期运行或 E4 级交叉校核证据。

## Decisions

### 1. 输入以“场景输入包”为单位，而不是零散文件

模块的外部输入单位是一个带清单的场景输入包，至少表达：包标识与版本、目标场景、
时间范围与步长、数据集条目清单、跨域映射条目、随机种子引用和公共 schema 版本。

判定与拒绝以包为单位提交结果：要么产出可用（含受限标记）的输入视图，要么产出
包级拒绝结论加逐条错误，不允许出现“部分加载成功但状态不完整”的中间产物。

替代方案是让下游模块各自读取所需文件。这会让同一次运行出现多套时间、单位和
ID 口径，也无法形成统一的启动前拒绝点，因此不采用。

### 2. 数据集条目与数据内容分离登记

每个数据集条目独立于其内容登记：稳定数据集标识、语义类别（配网拓扑、常规负荷、
车辆/行程、交通、充电设施、动作/事件模板、约束/指标定义）、版本、来源类型、
位置类别、完整性证据、质量状态和共享边界。

位置类别至少区分：仓库内、仓库外受限、生成自固定参数。仓库外受限条目只登记
标识、版本、哈希和位置类别，不登记个人绝对路径。

这样 `jun30-parity-baseline` 这类“已被使用但无法交付和校验”的输入可以被如实
表达为受限且缺完整性证据，而不是被写成正常输入。

### 3. 校验分层且顺序固定，先包级后对象级

校验按固定顺序执行，前一层失败不进入后一层：

```text
L1 包级：schema 主版本、清单完整性、时间范围与步长、种子引用
L2 来源级：数据集标识、版本、来源类型、位置类别、完整性证据
L3 身份级：对象公共 ID 的存在性、唯一性、类型/命名空间
L4 度量级：单位、符号约定、数值域、时间戳与采样周期
L5 引用级：车辆—道路、车辆/会话—站点、站点/聚合负荷—配网、负荷—配网
L6 质量级：缺失、估算、受限、不可用状态与本次运行的可用性判定
```

固定顺序让错误可解释：单位错误不会被伪装成引用错误，缺失来源不会先触发一堆
下游引用报错。替代方案是并行收集全部问题再排序，但在缺少来源或 schema 不兼容时
继续解析会产生无意义的次生错误，因此不采用。

### 4. 缺口区分“阻塞启动”与“受限可用”

模块不自行决定业务可接受性，而是按场景配置声明的必备条目集合判定：

- 必备条目缺失、无法解析或质量为不可用 → 包级拒绝，禁止启动；
- 非必备条目缺失或质量为估算/受限 → 允许启动，但输入视图与运行证据必须标记
  受限，并列出受限条目和影响的需求/指标；
- 受限输入不得被下游当作有效事实用于声明可复现或指标达标。

替代方案是缺失即全部拒绝。在正式项目数据尚未取得的当前阶段，这会让任何薄切片
都无法运行；而静默补默认值又会污染证据链，因此采用显式受限标记。

### 5. 转换只在入口边界发生并留痕

单位换算、时区归一、时间重采样、标幺值基准换算和 ID 命名空间映射只允许在本模块
入口完成。每次转换记录原始值/原始单位/原始时标、目标形式、规则标识和执行位置。

模块不猜测缺单位、缺时区或含义不明的字段，直接返回度量级错误。下游模块不再做
二次换算，避免同一物理量出现多次隐式转换。

### 6. 输入侧证据与运行证据对齐

模块输出一份输入侧证据记录，至少包含：包标识与版本、schema 版本、数据集条目
及其版本/哈希/质量、转换记录摘要、跨域映射版本、随机种子引用、判定结论
（可用/受限可用/拒绝）和生成时间。

该记录是上层 `运行证据可复现` Requirement 在输入侧的具体落点。缺少哈希或版本的
条目必须在记录中标记为不可独立校验，回放差异分析不得把这类输入当作已固定输入。

### 7. 参考项目只作为来源和对照，不作为格式

参考项目的文件格式、字段名、对象数量和样例值只用于发现字段和交叉对照。公共输入
契约独立定义，并要求公共 ID 独立于 DataFrame 索引、行号和内部类实例。

若某字段目前只能从参考项目获得，条目质量登记为参考/受限，并在缺口中记录正式
数据来源待取得，不改变契约本身。

### 8. 模块内部由 member 决定，公共语义变更须先修订上层

member 可自行决定：内部类与函数划分、目录结构、解析与缓存策略、错误码细分粒度、
配置文件语言、测试组织方式和性能优化手段。

需要改变公共身份、时间/单位语义、动作生命周期、适配边界或引用完整性规则时，
先提出上层 spec 修订，经 lead 与 Reviewer 批准后再继续，不在模块 PR 中静默改变。

## Data and Interface Contracts

本 change 不定义字段名与序列化形式，只定义必须表达的语义槽位。

### 场景输入包（模块输入）

| 语义槽位 | 最低要求 |
| --- | --- |
| 包身份 | 稳定包标识与版本 |
| 目标场景 | 场景标识与版本 |
| 时间上下文 | 带时区的起止时间、步长、`step_index` 起点 |
| schema | 公共 schema 版本声明 |
| 数据集清单 | 每类必备/可选条目及其数据集标识与版本 |
| 跨域映射 | 映射条目、端点类型与映射版本 |
| 随机性 | 随机种子或其引用 |
| 必备集合 | 本次运行判定为必备的条目列表 |

### 数据集条目

| 语义槽位 | 最低要求 |
| --- | --- |
| 标识与版本 | 稳定数据集标识与版本 |
| 语义类别 | 七类数据之一或约束/指标定义 |
| 来源类型 | 项目正式数据、参考项目资产、公开标准算例或固定参数生成 |
| 位置类别 | 仓库内、仓库外受限、生成自固定参数 |
| 完整性证据 | 哈希或明确的“无完整性证据”声明 |
| 质量状态 | 有效、估算、受限、缺失或不可用 |
| 共享边界 | 可入库、仅项目组内、禁止分发 |

### 输入视图（模块输出）

| 语义槽位 | 最低要求 |
| --- | --- |
| 判定结论 | 可用、受限可用或拒绝 |
| 定义对象集合 | 配网、车辆/行程、道路、站点/桩等带公共 ID 与版本的定义对象 |
| 时序输入集合 | 带对象引用、时标、单位、质量和来源的时序值 |
| 跨域映射集合 | 已校验端点与映射版本 |
| 时间与单位上下文 | 统一后的时间语义与单位约定 |
| 受限说明 | 受限条目、原因和受影响需求/指标 |
| 输入侧证据 | 决策 7 定义的证据记录 |

### 输入错误分类

| 类别 | 触发条件 | 调用方期望动作 |
| --- | --- | --- |
| schema 不兼容 | 公共 schema 主版本不支持 | 升级或改用兼容输入，不降级解析 |
| 清单不完整 | 必备条目缺失或清单自相矛盾 | 补齐条目后重试 |
| 来源不可确定 | 缺来源类型、版本或位置类别 | 补充来源登记 |
| 完整性缺失 | 正式输入缺哈希且被判定为必备 | 补充完整性证据或降级为受限 |
| 身份冲突 | 公共 ID 重复、缺失或类型不符 | 修正输入标识 |
| 度量非法 | 单位未知、符号不明、数值越域、时标不可解析 | 修正字段，不猜测 |
| 引用不可解析 | 悬空引用、端点类型不兼容、映射版本缺失 | 修正映射或对象集合 |
| 质量不可用 | 必备条目质量为缺失/不可用 | 取得数据或改变必备集合 |
| 内部错误 | 模块自身异常 | 重试或上报，不视为输入问题 |

错误至少表达类别、可定位对象/条目、期望与实际、是否可重试和当前是否允许启动。

## Risks / Trade-offs

- [与 Issue #23 的模块名称和数据流不一致] → 本 change 只定义外部契约与语义槽位；
  模块名称、目录和运行入口以 lead 的总体架构为准，Review 时逐项对齐，冲突时先
  修订上层而不是在本 change 自造名称。
- [受限可用被滥用为“已验证”] → 受限标记必须进入输入视图和输入侧证据，并列出
  受影响需求/指标；受限输入不得支撑可复现或指标达标结论。
- [契约过细，提前锁死实现] → 只规定语义槽位与判定行为，不规定字段名、格式和存储。
- [契约过粗，成员仍需猜测] → 每项 Requirement 配可判定 Scenario，覆盖正常路径与
  至少一条拒绝路径。
- [正式数据长期缺失导致契约无法验证] → 允许用固定参数生成的最小示例输入验证判定
  逻辑，但示例条目须登记为生成来源，不冒充项目正式数据。
- [仓库外数据被误提交] → 位置类别与共享边界为必填；`.gitignore` 与 PR 检查保持
  只登记标识/哈希，不登记个人绝对路径。
- [OpenSpec CLI 在本机不可用导致校验缺失] → 在 PR 中如实记录无法执行的命令，
  提供结构自检与 `git diff --check` 等等价检查，由 Reviewer 侧补充校验。

## Migration Plan

1. `member` 提交本 change 的 proposal/design/spec/tasks 与成果文档，不含运行时代码。
2. `lead` Review 契约是否与 `unified-ev-grid-data-model`、总体架构和 Issue #23
   的薄切片数据流一致，并裁定开放问题。
3. Review 通过后，本 change 作为数据准备/场景输入模块的实现依据；实现在后续
   change 中完成，并按本 spec 的 Scenario 建立正常与拒绝路径测试。
4. 实现阶段若发现契约不可行，先修订本 change 或上层 spec，再改实现。

回滚方式：删除本 change 目录与成果文档即可，不影响已归档 change、已接受 spec 和
既有研究资产。本 change 不引入代码依赖，因此无数据或接口迁移风险。
