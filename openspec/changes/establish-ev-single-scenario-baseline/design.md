## Context

仓库已有 EV 研究代码、V2Sim 快照、世界模型/拓扑设计材料和可执行的编排与回放检查，但这些内容都是供新系统重新开发时调研的参考资产，不是代码基线或验收基线。部分文档仍沿用“V2Sim 为主内核”的旧表述。2026 年 7 月 10 日正式进度安排已将目标收敛为“孪智融合配电系统运行架构方案评估模块”，并要求在 7 月 17 日前形成需求、场景调研和孪智功能映射三项成果。

参与者按职责只区分 `lead` 和 `member`；其中 `member` 代表两名固定组员。所有人均可能使用 Codex，因此成果结构、任务边界和验收方法必须在仓库内可机器读取，不能只存在于口头沟通中。

## Goals / Non-Goals

**Goals:**

- 建立三项正式成果之间的稳定追踪关系。
- 让两名组员自行协作和分工，同时避免对同一业务语义作出不同假设。
- 把现有研究材料转化为“已复现参考、待验证假设、后续需求”三类输入，并与新系统实现状态严格分开。
- 为工具选型和统一数据模型两个后续 change 提供明确输入。
- 用交叉 Review 与 lead 验收区分“已提交”和“已验收”。

**Non-Goals:**

- 不在本 change 中编写或重构运行时代码。
- 不确定最终仿真工具、公共接口 Schema 或多场景架构细节。
- 不把当前拓扑演示、研究文档或 Codex 结论直接视为验收完成。
- 不把 v1、V2Sim 或后续调研项目指定为新系统的代码基线；是否采用其中任何实现须由后续设计、选型和测试决定。

## Decisions

### 1. 三份成果独立版本化，以需求 ID 连接

《软件需求分析报告》负责定义系统边界和规范性需求；场景调研报告负责业务事实、数据来源、假设和候选方案；映射表负责逐行追踪。需求使用 `REQ-EV-<三位数字>` 作为稳定标识，三份文件引用相同 ID。

替代方案是把所有内容写入一份大文档，但这会增加两名组员同时编辑冲突，也不利于后续将调研和映射分别更新为附件，因此不采用。

### 2. Markdown 为仓库基线，正式格式从基线导出

三项成果首先以 UTF-8 Markdown 提交到 `docs/deliverables/`，以便 Review、diff 和 Codex 使用；需要 Word、Excel 或 PPT 时从已验收内容导出，并把导出文件作为同一版本的交付附件。

替代方案是直接多人编辑 DOCX/XLSX，但无法稳定 Review 行级差异，因此不作为源文件。

### 3. 只固定 lead/组员边界，不预分两名组员方向

- lead：需求报告、场景-业务-孪智功能映射、Spec、一致性与最终验收；
- member：两名组员共同承担 EV 场景调研、V2Sim 运行证据、候选仿真工具预研和交叉 Review；
- 每个 Issue/PR 在实际开始时确定一名直接负责人，另一名组员或 lead Review，下一任务可以重新分配。

这样不提前锁死两名组员的技术方向，也防止 lead 成为所有内容的唯一作者。替代方案是长期固定两套岗位，但当前人员少、任务变化快，会造成不必要的管理负担，因此不采用。

### 4. 参考代码库不构成新系统基线

`docs/世界模型调研报告.md`、`docs/世界模型原型设计书.md`、`ev_charging_v1/`、V2Sim 和后续调研项目只用于提取业务概念、候选算法、数据格式、接口经验和测试思路。参考代码可以被复现和比较，但其类名、目录结构、数据文件、测试结果和完成状态不得直接继承为新系统设计或验收结论。

三项成果必须分别记录：新系统目标组件与实现状态、参考资产与复现状态。即使参考项目已经通过命令验证，新系统对应需求仍应保持“规划中”，直至新系统独立实现并产生自己的测试证据。后续若决定采用某段参考实现，必须在对应设计/实现 change 中记录选型理由、接口适配和新系统测试结果。

### 5. 本阶段只记录工具选择约束

本阶段要求列出配电网仿真精度、数据需求、接口方式、连续运行、可复现性和许可等选择标准；OpenDSS、GridLAB-D、pandapower/PowerModelsDistribution 的实测与最终决定由下一 change 完成。

## Data and Interface Contracts

本 change 不定义运行时 API，但三项成果至少使用以下共同列/概念：

| 字段 | 含义 |
| --- | --- |
| `requirement_id` | 稳定需求标识，如 `REQ-EV-001` |
| `source` | 任务书意图、正式计划或批准决策 |
| `scenario_step` | 业务流程步骤或异常流程 |
| `input_state` | 输入数据和孪生体状态 |
| `twin_responsibility` | 物理状态、演化和校验责任 |
| `agent_responsibility` | 感知、预测、建议或动作提案责任 |
| `target_component` | 新系统重新开发时承担该责任的目标组件，不使用参考项目类名替代设计 |
| `tool_model_component` | 新系统所需的确定性工具、模型或校验组件 |
| `action_event` | 控制动作或外部事件 |
| `constraint` | 物理、安全、数据或业务约束 |
| `metric` | 可计算评价指标 |
| `evidence` | 新系统自身的测试、数据、接口、演示或文档证据；参考库证据不得填入此列 |
| `status` | 新系统目标状态：已验证、部分具备、规划中、待裁定 |
| `reference_assets` | v1、V2Sim 或其他调研项目中与该需求相关的参考位置 |
| `reference_evidence` | 仅证明参考项目可复现的命令、结果或文档锚点 |
| `reference_status` | 参考状态：已复现、部分可参考、待调研、不适用 |

## Risks / Trade-offs

- [任务书条款未精确编号] → lead 在验收前补充可定位的章节/条款引用，暂不能定位的内容标为待裁定。
- [Markdown 与最终办公文档存在格式差异] → Markdown 作为内容基线，导出件在阶段成果提交时做版式验收。
- [参考项目被误当成新系统基线] → 正式计划和当前 change 是需求与验收基线；目标状态与参考状态分栏记录，参考复现结果不得计入新系统完成度。
- [小组规模导致 Review 资源紧张] → 每个 PR 只设一个主成果，由另一名组员或 lead Review。
- [需求阶段提前陷入工具争论] → 只记录选择约束，把工具实测与决定放入下一 change。

## Migration Plan

1. 将正式 DOCX 纳入 `docs/`，同步替换旧 Markdown 计划。
2. 合并本 change 后按主要成果创建 GitHub Issue，允许相邻周任务在一个两周窗口内并行推进。
3. 组员在各自 fork 的独立短期分支完成成果并通过 Review。
4. lead 执行一致性检查和最终验收，合并成果 PR。
5. 将已验收 change 归档为主 spec，随后创建工具选型和统一数据模型 change。

如本基线需要回滚，恢复正式计划文件不变，回退本 change 与治理文档提交；不得回退或删除已有研究代码和原始材料。
