## Context

`REQ-EV-001`—`REQ-EV-012` 已经定义场景加载、车辆/交通/充电、配网、
孪智交互、事件回放、异常和指标需求。V2Sim 与 pandapower 的阶段调研进一步
暴露了三个问题：

1. 候选项目使用各自内部对象、单位和结果结构，不能直接成为新系统合同；
2. 车辆、交通、充电站和配网的时间、对象 ID 与动作语义尚未统一；
3. 参考项目能够运行不等于新系统具有可追踪、可拒绝、可回退和可复现的接口。

本 change 是系统级设计 change。`lead` 规定跨模块必须一致的语义和边界；
`member` 在独立 change 中细化模块字段、内部状态机、转换实现和测试。成员
change 必须引用本 change 的 Requirement/Scenario，不能自行改变公共契约。

## Goals / Non-Goals

**Goals:**

- 定义独立于 pandapower、OpenDSS、V2Sim 和 v1 的系统级数据语义；
- 让静态对象、时序状态、事件、动作、结果、错误和指标可以相互追踪；
- 保持孪生体事实/校验责任与智能体动作提案责任分离；
- 为配网、EV/交通、充电设施和结果评估模块提供稳定适配边界；
- 支持单场景实现，并保留多场景、三相配网和其他后端扩展能力；
- 让组员能够从上层契约继续编写模块级 OpenSpec，而不需要猜测跨模块语义。

**Non-Goals:**

- 不在本 change 中确定 Python 类、数据库表、文件格式或序列化框架；
- 不固定每个领域的全部字段和内部状态机；
- 不实现运行时代码、PoC 适配器或数据迁移程序；
- 不用候选项目对象规模、样例值或私有字段约束新系统；
- 不宣布 pandapower、OpenDSS 或 V2Sim 为最终生产后端。

## Decisions

### 1. 采用“公共语义内核 + 领域模块 + 后端适配器”三层模型

公共语义内核定义身份、时间、单位、版本、来源、状态/事件/动作包络、结果、
错误和证据元数据。领域模块拥有配电网、车辆/交通、充电设施等事实状态。
后端适配器只负责新系统合同与候选工具之间的转换和执行。

```text
场景/运行上下文
        │
公共语义内核：ID、时间、单位、版本、来源、事件、动作、结果、错误
        │
 ┌──────┼─────────┬──────────┬───────────┐
配电网领域   EV/交通领域   充电设施领域   孪智交互/安全校验
        │           │           │
 pandapower/     V2Sim/其他    站点模型/数据源
 OpenDSS/其他
```

替代方案是直接统一候选工具的内部对象，但这会把上层代码绑定到 DataFrame、
V2Sim 类和特定版本，无法独立测试、替换或交叉校核，因此不采用。

### 2. 系统级模型只规定跨模块契约，模块内部由成员 change 细化

本 change 规定：

- 每类公共对象和消息必须表达的语义；
- 跨模块引用、时间和单位一致性；
- 动作从提案到执行/回退的状态转换；
- 适配器输入输出、结果和错误的最低边界；
- 可复现和验收所需的元数据。

成员 change 可以自行决定模块内部类、数据结构、算法、缓存、文件拆分和局部
字段，但必须说明如何映射到上层契约。若需改变上层语义，先修改本 change，
Review 后再继续实现。

替代方案是由 lead 写完所有字段和内部实现，但这会剥夺组员的设计责任，也会
让系统级 spec 过早绑定尚未验证的技术细节，因此不采用。

### 3. 身份、时间、单位、版本和来源是所有可交换对象的共同语义

所有跨模块对象、状态、事件、动作、结果和错误至少具有以下语义：

| 语义 | 系统级要求 |
| --- | --- |
| 身份 | 稳定、唯一、带类型/命名空间的对象或消息 ID；不得直接使用候选后端行号作为公共 ID |
| 运行 | `run_id` 将配置、输入、动作、事件、状态和结果归入同一次实验 |
| 时间 | 同时表达带时区的绝对时间、相对仿真步 `step_index` 和时间步长；禁止隐式本地时间 |
| 单位 | 数值必须绑定明确单位；转换发生在边界并保留原始单位/来源 |
| 版本 | 声明 schema、数据集、模型/后端、策略和生产者版本 |
| 来源 | 记录来源类型、位置/标识、生成方式和可选哈希；不得伪造缺失正式数据 |

具体字段名和序列化表示由模块 change 决定，但语义不得缺失。

### 4. 区分定义、时序值、状态快照和事件

- **定义对象**：相对稳定的身份、拓扑和设备/车辆/站点参数；
- **时序值**：带对象引用、时标、单位和质量状态的连续或离散观测；
- **状态快照**：同一 `run_id`、`step_index` 和版本下的一致事实视图；
- **事件**：在明确时间对明确对象发生的离散事实或外部注入，包含类型、来源、
  负载、影响对象和因果/关联 ID。

状态快照不能混入未经批准的未来智能体提案；回放以已记录事件和已接受动作
为输入，不隐式重新调用非确定性智能体。

替代方案是只维护一张“当前状态大表”，但它无法支持事件回放、并发版本、
异常溯源和跨模块一致性检查，因此不采用。

### 5. 动作采用显式生命周期，孪生/安全校验层拥有原子提交权

动作生命周期至少区分：

```text
proposed
   ├─ rejected
   └─ accepted → executing → executed
                         └─ failed → rolled_back / safe_fallback
```

动作必须关联提议者、目标对象、有效时间、参数、策略版本、状态快照版本和
校验结果。`accepted` 只表示通过校验，`executed` 才表示状态已经原子提交。
任一阶段失败不得留下跨模块半提交状态。

后端适配器只能执行已接受动作并返回结果/错误，不能自行把智能体提案升级为
已接受动作。

### 6. 配网与场景后端通过窄适配契约隔离

配网适配器的系统级输入至少包含版本化拓扑、设备参数、常规/EV 聚合负荷、
已接受动作、时间上下文和单位；输出至少包含收敛状态、母线电压、支路功率/
载流、网损、约束越限、结构化错误和运行元数据。

EV/交通/充电后端的系统级输入输出必须映射到车辆、行程、道路、站点、会话、
事件和时序值，不向上层暴露候选私有对象。

适配器可以保留后端原始结果作为诊断附件，但上层只消费统一结果/错误合同。

### 7. 结果、错误、指标和证据必须结构化并可追踪

结果必须关联 `run_id`、输入/配置版本、动作/事件、时间和生产者。错误至少
区分输入校验、引用完整性、时间/单位、后端不可用、求解不收敛、动作违规、
超时、执行失败和内部异常，并给出是否可重试及安全状态。

指标定义与指标值分开版本化。指标定义包含口径、单位、时间窗口、聚合方法、
缺失值处理和基准方案；指标值必须可回链到原始结果和运行证据。

替代方案是只保留日志字符串和报表值，但无法支持自动拒绝、回放、跨后端
比较和验收追踪，因此不采用。

### 8. Schema 演进采用显式版本和边界转换

公共合同声明 `schema_version`。模块读取不支持的主版本时必须拒绝；兼容的小
版本演进由模块级 change 规定。旧版本转换必须是显式、可测试、可记录的边界
操作，不允许运行时静默猜测字段含义。

本 change 不选择具体版本规范或序列化库；成员 change 需要给出模块字段版本、
转换规则和兼容性测试。

### 9. 基础数据清单是来源/缺口账本，不是运行时 Schema

`电动汽车场景基础数据清单` 逐项记录对象/字段组、来源、单位、时间粒度、
对象 ID、证据、质量、许可/共享边界、缺口和后续模块归属。它用于支撑模型
设计和数据获取，不直接作为运行时文件格式。

参考项目样例可以登记为“参考/已复现”，但正式输入缺失时必须记录缺口，
不得把样例静默提升为项目正式数据。

## Risks / Trade-offs

- [系统级模型过于抽象，组员仍需猜测] → 每项 Requirement 配具体 Scenario；
  成员 Review 时必须指出无法细化的语义，lead 在批准前裁定。
- [系统级模型过细，限制成员设计] → 只固定跨模块语义和最低边界；内部字段、
  类、存储和算法留在模块 change。
- [同一语义出现多个 ID/单位/时标] → 基础数据清单与模块 spec 必须显式映射到
  公共身份、单位和时间语义，并在转换边界测试。
- [候选后端对象泄漏到上层] → 适配器测试检查公共输出不包含候选私有对象；
  原始结果仅作为诊断附件。
- [动作执行出现半提交] → 模块级设计必须给出事务/补偿或快照回退方案；没有
  失败路径证据不得验收。
- [Schema 版本长期漂移] → 所有公共消息记录 schema/producer 版本；不支持版本
  明确拒绝，不静默降级。
- [本周只有一名 member，Review 与产出冲突] → member 优先完成基础数据清单和
  系统级 spec Review；Issue #14 顺延，不压缩本 change 的公共契约 Review。
- [把设计完成写成运行时完成] → 文档状态和 PR 明确“设计基线”；新系统状态仍由
  后续实现、测试和运行证据更新。

## Migration Plan

1. `lead` 完成本 change 的系统级 proposal/design/spec/tasks。
2. `member` 恢复场景调研报告并形成基础数据清单，Review 上层对象和数据边界。
3. `lead` 根据 Review 收敛统一数据模型设计说明书和软件设计规格书初稿。
4. 成员从获批上层 change 建立独立模块级 change，细化字段、校验、错误和测试。
5. #12 设计成果验收后，#13 才能创建可删除的 pandapower 适配器 PoC。
6. 后续实现 PR 必须通过适配边界、动作生命周期、错误和可复现性 Scenario。

若系统级设计未通过 Review，删除本 change 和未合并文档即可回滚；不得据此
删除已有研究资产。若后续实现发现公共契约不可行，先以新 OpenSpec 修改契约，
再迁移模块实现，不直接修改已归档 spec。
